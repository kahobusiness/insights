# 🏗️ Two Ways to Grow the Same Mall Agent: wanda-agent vs. wanda-agent-release

<Callout type="info" emoji="🧭">

This post is based on snapshots of both repositories from early September 2026. `wanda-agent` is the monolithic demo of the Wanda Plaza "mall companion" agent; `wanda-agent-release` is the componentized platform that grew out of the same business, which the repo calls tbox-app. Both were built by people working with coding agents. Every design quote below comes from each repo's own AGENTS.md, docs, or Agent Notes.

</Callout>

The two repositories do the same job: an AI assistant for a shopping mall that checks membership points, looks up parking and pays the fee, claims coupons, recommends brands, and runs promotional activities.

They also sit on the same foundation: Mastra for orchestration, the Vercel AI SDK for model calls, the AG-UI event protocol for streaming, WebSocket for transport, and the TBox platform SDK for conversations and knowledge bases.

Their timelines almost overlap. Yet put the two trees side by side and they have completely different shapes.

| | wanda-agent | wanda-agent-release |
|---|---|---|
| Time span | 2026-07-30 → 08-24 | 2026-08-03 → 09-06 |
| Commits / authors | 59 / 4 | 1621 / 10 |
| Repo shape | pnpm workspace, two packages: `client` + `server` | pnpm monorepo: contracts + SDK + 6 business modules + 3 providers + 4 templates + CLI |
| Orchestration layer | `@mastra/core` 0.10, `ai` 4.3 | `@mastra/core` 1.59, `ai` 6.0 |
| Core server file | `agent-service.ts`, 3161 lines, business and framework mixed | `chat-engine.ts`, 2058 lines, zero business vocabulary |
| Test files | 87 | 316 |
| CI and gates | none | three parallel CI jobs, 21 doctor rules, 5 guard scripts |

In one sentence: the first repo answers "can the demo run?", the second answers "what happens when the second mall shows up?"

Below I take the difference apart along eight cuts.

## 1. Shape of the Tree: Two Packages Doing Their Own Thing, or Layers with One Direction

The structure of `wanda-agent` is plain:

```text
wanda-agent
├── client/   Taro 4 · React · zustand         ~18k lines
├── server/   Express · ws · Mastra             ~14.6k lines
└── config/   8 JSON files (mall identity, component toggles, parking rates, activity snapshot…)
```

There is no shared package between the two and not a single cross-package import. The only root config the client reads is `chat.json`, bundled at build time. In other words, there are no layers here, only ends.

`wanda-agent-release` is a layered tower:

```text
wanda-agent-release (tbox-app)
TIER0  packages/contracts        protocol types and constants, zero dependencies
       packages/app-sdk          chat-engine · registries · card pipeline · auth · memory
TIER1  modules/contracts-mall    mall Port interfaces · card zod schemas · assembler
       modules/module-*          member / parking / promotion / shopping-guide …
       modules/provider-*        mock / wanda / joycity
       templates/template-agent* base / mall / support application templates
       cli/                      create · module add/remove/update · doctor · card preview
          ↓ tbox-app create, then module add
       generated application     apps/{server,client} + packages/{module-*,provider-*}
```

Dependencies only point upward: business modules depend on the SDK and contracts, providers depend on `contracts-mall`, the SDK may not import anything from TIER1, and modules may not import each other. None of this is a verbal agreement. It is the `workspace-dag` rule in the CLI's doctor, and violating it fails the check.

The axis of the split is "what will change". The earliest design document in the repo puts it bluntly:

> Layered hybrid model: split along the code's axis of change. The security boundary runs as an SDK black box; domain implementations are distributed as source.

Security logic and the framework core run as an SDK black box that business teams physically cannot modify. Domain implementations like membership and parking ship as source code into the application, where teams can change whatever they like. A pure-SDK approach was rejected because extension points would balloon into a DSL. A pure-source approach was rejected because of the risk of financial loss.

## 2. How One Message Travels

The similarities first. Both sides only use WebSocket, because Alipay mini programs do not support SSE. Both use AG-UI event streams. Both wrap the AI SDK in a Mastra Agent to call an OpenAI-compatible endpoint. Both run the same hybrid orchestration: deterministic direct routes first, model as fallback.

Now the differences. The `wanda-agent` path:

```text
SEND_MESSAGE
→ ws-server verifies the actor token
→ agent-service.chat()
   ├─ 21 detect* functions match fixed phrases or regexes in order
   │    hit → run*Direct: server emits the card, then a hidden model call writes one guiding sentence
   └─ miss → constrained LLM does single-label intent classification (8s timeout) → full Agent
→ Mastra agent.stream(history)
→ tool returns { presentation: { kind: 'mall.xxx-card', … } }
→ AG-UI TOOL_CALL_RESULT
→ client dispatches to a card component through an if-chain keyed on the kind string
```

The `wanda-agent-release` path:

```text
HELLO (carrying the mallId scope) → HELLO_ACK
SEND_MESSAGE
→ chat-engine.chat()
   ├─ matchIntent: intent routes contributed by modules → handler registry, zero-LLM direct output
   ├─ preTools: BM25 routing pre-recall, 2s budget per tool; concurrent memory recall, 600ms
   ├─ skills: inject the module's SKILL.md by routing terms (full SOP or recap)
   └─ compose the user message in a fixed order: card decision → preTool → memory → skill → user text
→ Mastra agent.stream(history)
→ tool returns { …facts, cards: [{ cardType, data }] }
   → platform validates against CardRegistry, pools them, strips to { id: 'c1', cardType }
→ model names the cards to show with a tag at the end of its reply
→ platform arbitrates: in order / model abstains / fallback to the last card in the pool, max 3 per turn
→ CUSTOM event tbox:card
→ client looks up the cardType in a registry and renders
```

Two differences deserve attention.

**First, who owns the deterministic routes.** Both sides have the same motivation, and a comment in `wanda-agent` states it plainly: "weak models copy the historical pattern after several turns and skip the tool call, so execute on the server side and replay the same event sequence." The difference is where it lives. `wanda-agent` stuffs all 21 detect functions and their run counterparts into `agent-service.ts` and picks a path with one long ternary chain. `wanda-agent-release` lets each module contribute its own intent routes and handlers; the platform only collects and dispatches.

This is not a matter of taste. Among the twelve root causes listed in the platform design document, item 4 reads:

> Core files heavily modified, upgrades break: `agent-service.ts` grew from 696 lines to 2988 through 6990; the registry file was completely rewritten.

When one file holds both framework and business, every template upgrade collides with business changes.

**Second, the order is frozen.** `wanda-agent-release` has a design principle called "prefix cache stability", spelled out as three iron rules: the tool set is unconditionally constant, the system prompt is constant, and personalized data flows through exactly one channel at the front of the user message. So the system prompt is pure platform instructions plus one business section; anything that changes per turn (pre-recall results, memory, skills) is spliced in a fixed order ahead of the user text; history is appended verbatim with no rewriting. Across multi-turn conversations the KV cache keeps hitting.

`wanda-agent` has no such constraint. Its system prompt is one 82-line block that hardcodes tool IDs and trigger phrases line by line, and the guiding sentence for a direct route requires an extra hidden model call. It works, but nothing was designed around cache hit rates.

## 3. Organizing Capabilities: Scattered Across Packages, or One Package for Both Ends

This is the most fundamental difference between the two.

In `wanda-agent`, "parking" is not a directory. It is a set of files scattered across two packages: tool definitions, domain services, detection and execution inside `agent-service.ts`, REST routes, prompt paragraphs, client parsers, card components, a registry, and if-chain branches. Working backward from the repo's own AGENTS.md and code, adding one capability touches roughly these places:

```text
server/src/tools/<x>.ts                      tool implementation
server/src/components/definitions.ts         register the tool ID and its component
server/src/tools/registry.ts                 add to the tool catalog
config/components.json                       component toggle
server/src/agent/agent-service.ts            detect function + run*Direct + ternary chain
server/src/agent/prompts/wanda.ts            one more prompt paragraph
client/src/components/<X>Cards/              types / parser / component / styles
client/src/components/MallMessageCards/registry.ts   register the card contract
client/src/components/JoycityMessageCards/index.tsx  add a kind branch
client/src/pages/index/service-queries.ts    home-page quick entry
tests on both ends + the evals dataset
```

A dozen or so places, across two packages. Config files can only toggle: `components.json` holds 8 components, each with an `enabled` flag. Trigger phrases, image domain allowlists, activity IDs, and the mall name all live in code. The same phrase, "brand guide", is maintained in three places: a server regex, a client quick entry, and the system prompt.

`wanda-agent-release` folds one capability into one npm package, with server and client code living together:

```text
modules/module-member/
├── tbox.component.json        declares contributes: tools / cards / handlers / service slots
├── skills/member/SKILL.md     prompt fragment + routingTerms
├── src/server/
│   ├── index.ts               serverModule = { declaration, cards, skills, preTools, register(ctx) }
│   ├── tool.ts                query-points tool, output carries cards
│   ├── handler.ts             direct intent output
│   └── cards/<cardType>/meta.ts
└── src/client/
    ├── index.ts               clientModule = { cards, register(ctx) }
    └── cards/<cardType>/index.tsx
```

`register(ctx)` registers and never resolves. The platform's `registerServerModules` injects ctx into each module in turn, and `build-engine` gathers every registry and merges them into the engine. Modules cannot import each other; cross-module interaction always goes through the service registry on ctx.

Installing a module into an application is the CLI's `module add`: pull the source package from npm, rewrite the package name and imports to `@app/module-member` with the TypeScript AST, insert one import line and one array entry in the anchored region of the app's `modules.ts`, record a baseVersion in `.tbox/app.json`, generate mock bindings if `integrations.json` is missing, then run doctor. The repo calls this "the development shape and the published shape are isomorphic": a module's published artifact is its source, the module expanded into the app is identical to the one in the repo, and later upgrades use a 3-way merge.

One empirical number underpins the design. The design document notes:

> Empirical data shows that in two real applications, genuinely business-specific code is only about 30%; 70% is reusable framework logic.

If 70% is reusable, then "fork a copy per mall and modify it" is clearly the wrong way to organize.

## 4. Card Contracts: String Conventions, or a Shared Schema plus a Three-Party Protocol

Cards are the core interaction surface of this kind of agent, and this is where the two diverge most.

The `wanda-agent` approach:

+ The server validates tool output with a zod schema; the client hand-writes a separate set of TS types and pairs them with a defensive parser that checks exact key sets, date formats, and an image domain allowlist
+ The contract key is a `kind` string; new `mall.*` contracts coexist with legacy `joycity.*` ones, and the last fallback parser is named `legacy-joycity-v1`
+ "Card kinds must not be renamed" lives in AGENTS.md, enforced by memory
+ The client can forge locally: after a payment succeeds, `buildWandaPaymentSuccessMessage` in `chat.ts` constructs a toolCall named `mallClaimedVouchers` and pushes it into the message list, while the server knows nothing about it
+ History stores text only; refresh the page and every card disappears

The design document lists the last three as root causes 9, 10, and 11: "history cards completely lost", "payment cards intercepted on the client, bypassing the server", "card protocol types manually mirrored".

The `wanda-agent-release` approach:

+ One zod schema in `contracts-mall`, referenced by both the server `meta.ts` and the client component; the app-side card type is inferred straight from the assembly array with `InferModuleCards`
+ Every card's `CardMeta` carries `cardType`, `dataSchema`, `sampleData`, `schemaVersion`, and an optional `migrate`; history restoration goes through the same schema plus migration
+ Three doctor rules watch it: `card-type-consistent`, `schema-version`, `sample-data-valid`; the `card preview` command renders a static preview from `sampleData`
+ Card emission is a three-party protocol: tool output only declares candidates, the platform validates, pools, and strips them, the model names the cards at the end of its reply, and the platform falls back so the turn is never empty

The three-party protocol deserves one more sentence. In `wanda-agent`, "tool returned" equals "card shown"; whoever calls the tool decides what is displayed. `wanda-agent-release` separates "eligible to show" from "shown this turn": the tool says "I have these", the model decides which and in what order based on the conversation, and if the model forgets or gets it wrong the platform falls back. The card meta used to carry `allowedTools` and `modelHint`; both were removed because cards should not bind back to tools.

## 5. Vendors and Tenants: One Repo per Mall, or slot / provider / binding

The AGENTS.md of `wanda-agent` states explicitly that "this repository is an independently buildable and deployable mall instance". `mallId` only validates config consistency; there is no runtime multi-tenancy. There is one OpenAI-compatible model provider. The migration from Hangzhou Joy City to Hangzhou Wanda was done by forking and editing.

The debt this path leaves is conspicuous: the package is still named `tbox-agent-template`, tool IDs are still `joycity*`, the points-mall product snapshot is still Joy City data from late July, and `docs/` still holds Joy City's open-platform API list. Worse, demo semantics are baked into the data structures: `mode: 'demo'` and `receiptKind: 'simulation'` are enum literals in the schema. Going to production is not a toggle flip but a whole new set of definitions.

`wanda-agent-release` splits this into three concepts:

```text
module manifest declares a need     module-member contributes.services: member.main
provider package declares supply    provider-wanda offers 6 slots, with signing strategy wanda-c-signed-v1
config/integrations.json            services.member.main = { provider: 'wanda', instances: { <mallId>: … } }
runtime resolution                  ctx.integrations.resolveService({ service, scope: { mallId } })
```

The mock, wanda, and joycity providers implement the same set of Port interfaces (`MemberAccountPort`, `ParkingQueryPort`, and so on). Mock is an in-memory implementation flagged `local: true`; clone the repo, configure no credentials at all, and every card still renders. Switching vendors means swapping the provider package and the binding file. Business modules do not change a line.

There is also a guard called `guard-vendor-neutrality`: it scans the 5 business modules, `contracts-mall`, `provider-mock`, and the factory surface of both templates, and fails the moment the words joycity, wanda, Joy City, or Wanda appear. AGENTS.md states it as an iron rule: "the business surface has zero vendor coupling; the only source of truth for vendor integration is the provider package."

Incidentally, the proposal to let one application mix two vendors was explicitly rejected. The late-August ruling was one application, one vendor, with instance-level overrides retained.

## 6. Writes and the Security Boundary

Card buttons in `wanda-agent` have two exits: backfill a fixed phrase into the conversation, or call a REST endpoint directly for plate registration, enrollment, or payment. Add the client-side forgery from section 4, and how much the server knows about payment state depends on whether the client is honest.

`wanda-agent-release` moves the entire write channel to the server:

```text
button → UI_ACTION { surfaceId, action: { actionId, contextToken } }
→ ws-server → component-action dispatcher
   session assertion → authorize → cardType check → inputSchema check → execute → effects
→ tbox:card-update / tbox:notice / tbox:effect
```

Every card ships with an HMAC-signed, single-use ActionGrant. The host effects a client can trigger (launch payment, launch authorization) form a closed union type with no custom slot. This is the concrete form of the line quoted in section 1: "security logic runs as an SDK black box that business teams physically cannot modify."

Doctor also has a `naked-write-route` rule specifically for catching bare write routes.

## 7. State, Memory, and Dual-Track Messages

`wanda-agent` keeps conversation history in an in-process Map; Journey state can be in-memory or Appwrite; `saveToConversation` stores text only.

`wanda-agent-release` introduces "dual-track messages". The in-memory history is the LLM track: Mastra's messageList ground truth is appended verbatim, zero loss, zero rewriting. The database is the render track: four fields, each pruned to a 60k budget while preserving shape, written one way and consumed only by the frontend. The two tracks never intersect and never flow back. This serves prefix cache stability, and it keeps "what the model sees" and "what the user sees" independently controllable.

Another interesting decision concerns context passing. `wanda-agent` uses AsyncLocalStorage to carry actor context. `wanda-agent-release` ran a context unification at the end of August that turned the identity channel into explicit parameters, and the note records a reversal across two review rounds:

> ALS correctness is a non-local invariant: a delayed callback fired inside someone else's run scope silently picks up the wrong identity, and "never capture inside a callback" cannot be expressed as an AST rule. Explicit correctness is locally visible, evident at the call site and mechanically enforceable by doctor.

The `toolCardScope` used for display data still keeps ALS, on the grounds that it carries best-effort display data whose risk level differs from identity data.

To be honest about it, the boundary at this layer is the same on both sides: single-instance, in-memory state. Restarts forget, replicas do not share, history grows without bound. The platform lists all of this under "known boundaries" in `runtime.md`. Going platform solved a structure problem, not a scale problem.

## 8. Engineering Guardrails: Remembered by People, or Caught by Machines

`wanda-agent` is not short on tests: 47 files on the server, 40 on the client. But there is no CI. The evals dataset has 20 cases, yet the replay runner mentioned in its README does not exist in the repo. A commitlint config is present; the husky directory was never committed. The rules live in AGENTS.md ("kinds must not be renamed", "never import the parent workspace") and rely on the reader's discipline.

`wanda-agent-release` turns as many rules as it can into things a machine can catch:

+ **21 doctor AST rules**: `workspace-dag`, `register-pure`, `singleton`, `sdk-internal-import`, `naked-write-route`, `card-type-consistent`, `schema-version`, `sample-data-valid`, and more
+ **5 guard scripts**: secrets, vendor-neutrality, workspace, visual, dev-probe, plus `verify-docs`
+ **lefthook**: pre-commit runs guard-secrets and verify-docs, pre-push runs typecheck
+ **CI**: three parallel jobs per PR (basic, mall fast path, support fast path), with a full nightly run
+ **Release**: `release.mjs` manages the topological publish order of 17 packages and reconciles three sources: git tags, `.release/state.json`, and the registry
+ **Release consent rule**: any write to a real registry requires the user's explicit consent; `--yes` and an implicit yes from a non-TTY do not count

Then there is documentation. `docs/reference/` holds 11 pages of architectural ground truth, and `.agents/notes/` holds about 250 Agent Notes filed under proposed, implemented, rejected, and archived, each recording why a thing was done and which alternatives were turned down. Code changes must update the docs in the same change, and `verify-docs` checks the format.

Why such weight on mechanical gates? The answer is the first design principle:

> P0 Coding Agent efficiency: every API shape is judged first by whether a coding agent guesses less, errs less, and round-trips less.

These guardrails exist first for coding agents. A person reads AGENTS.md and remembers. An agent starts each time with a fresh context, and what it needs is a check that fails on violation.

## 9. The Cost of Going Platform

By this point it is tempting to conclude that the platform crushes the monolith. But the costs are just as real.

**Complexity.** The same `pnpm-workspace` file must resolve in three contexts: root development mode points back to `workspace:*` through overrides, generated-app verification mode injects `file:` references to local tgz files, and production mode goes through the registry. To keep that mechanism intact, `guard-workspace` carries 5 dedicated rules: the catalog identity, vite anchors, relative filters, script mirroring, lockfile consistency. Platform packages also forbid peerDependencies, because pnpm's peer combinations would split them into multiple instances.

**Coordinated releases.** Under 0.x versioning a minor bump is breaking, and seven packages bump together.

**Drift.** The docs say app-sdk 0.15.0; the source says 0.14.0. The last entry in `.release/state.json` is from August 14. The base and mall templates are "twins with no sync mechanism"; shared capabilities must "land in base first, then be evaluated for backporting to mall".

**Abstraction risk from speed.** 1621 commits in five weeks, 10 authors. In early September the support template standardized capability onboarding as "capability package declaration + assembler + projection registry", and the note admits: "all three instances are lightweight; the risk of abstraction mismatch remains, and the assembler keeps an escape hatch."

Look back at `wanda-agent`: 59 commits, 4 people, the Wanda adaptation and an end-to-end demo done within two weeks. At the stage of "is this business real?", the monolith was the right call.

## 10. When to Switch to the Second Way of Growing

Putting the two repos side by side, these are the conclusions I draw:

+ **When the second mall shows up.** The `joycity*` debt that `wanda-agent` carried from its Joy City fork into Wanda is the trigger signal for going platform. One tenant does not need a provider abstraction; two tenants without one start copy-pasting.
+ **When the demo has to become production.** Is the write channel on the server, can history cards be restored, can payment state be queried back? The monolith lacks all three, and all three decide whether you can ship.
+ **When the main developers are coding agents.** An agent needs API shapes that require less guessing and gates that fail on violation, not implicit conventions inside a three-thousand-line file. The P0 principle, doctor, and Agent Notes in `wanda-agent-release` are all, at bottom, optimizing the repo for agents rather than for people.
+ **But do not build the platform for the first mall.** The platform repo itself spent five days taking its design from v2.0 to v5.0, cutting 8 registries down to 4 plus 1 and dropping the IoC container and the Transaction engine, before writing code. Without the evidence from a monolith phase, you do not know what to abstract and what to leave alone.

One table to close:

| Cut | wanda-agent | wanda-agent-release |
|---|---|---|
| Layering | ends only, no layers | TIER0 contracts → SDK → TIER1 contracts → modules / providers → templates → app |
| Direct routes | 21 functions in one 3k-line file | contributed by modules, dispatched by the platform |
| Capability organization | spread across two packages, a dozen edits to add one | one package for both ends, expanded by `module add` |
| Card contract | `kind` strings, one copy of the types per end | shared zod schema, schemaVersion plus migrate, three-party emission protocol |
| Vendors | one repo per mall, fork and edit | slot / provider / binding, neutrality guard |
| Write channel | client can call REST directly and forge tool results | server-side dispatcher, single-use grants, closed effect set |
| State | in-process Map, text only | dual-track messages, zero intersection |
| Gates | tests plus documented conventions | doctor + guard + lefthook + CI + release consent |
| Shared boundary | single-instance in-memory state | single-instance in-memory state |
